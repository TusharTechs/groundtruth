# Demo Guide

Everything below runs in DEMO MODE (deterministic, offline, no credentials)
unless stated otherwise. The demo narrative is identical on every run — that
is a feature, not a shortcut: it is what makes the system testable.

## The scenario

> "Find a genuine XZ-420 compressor for an ACME HVAC-200 within 25 km. It
> must be compatible, available today, under ₹25,000, and the supplier must
> hold it until 5 PM. You may request a hold, but do not purchase anything."

Six fictional Bengaluru HVAC suppliers (phone numbers are demo-fictional and
masked in the UI):

| Supplier | Distance | Scripted outcome |
| --- | --- | --- |
| Anand Cool Point | 9.3 km | "I think we have it" — hedged, cannot check → UNKNOWN |
| Kirloskar Spare Parts | 12.1 km | Out of stock; mentions Whitefield branch → FAILED |
| Bharat Climate Control | 15.0 km | No answer → UNREACHABLE |
| **Metro Components** | 18.4 km | In stock (2), compatible (checked the catalogue!), ₹22,800, pickup till 4:30 PM, hold **pending manager approval** |
| CoolTech Refrigeration | 22.7 km | Only XZ-420B revision — not compatible → FAILED |
| Sri Venkateshwara HVAC | 24.2 km | Everything works but ₹27,500 → over budget → FAILED |

## Run 1 — success path (the flagship)

1. Open `/` → **Verify Reality**.
2. The flagship request is pre-filled. Click **Analyze goal**.
   - Show *UNDERSTANDING YOUR REQUEST*: item, hard requirements (each with
     the exact phone question), preferences, and the authorized vs.
     prohibited action chips (✕ purchase).
3. Click **Start verification**. The dashboard takes over:
   - calls stream in one by one: CALL STARTED → dialing → live transcript
     turns → SUPPLIER ANSWERED → structured result → per-constraint events
     (`AVAILABILITY VERIFIED`, `COMPATIBILITY FAILED`, ...);
   - the strategist logs its decisions (`STRATEGY_DECISION` events);
   - at Metro Components, the first call ends with the hold *possible but
     unconfirmed* — the strategist fires an automatic follow-up; the second
     call returns "manager approved, held until 5 PM";
   - early stopping: CoolTech and Sri Venkateshwara are never called once
     Metro is fully verified.
4. Click the **Hold confirmed** claim chip → the evidence modal: verified
   claim, source, method, CALL-E call ID, confidence, and the supplier's
   quoted words ("We will hold one unit until 5 PM at the front desk").
5. The decision banner: **REALITY VERIFIED** — XZ-420, Metro Components,
   ₹22,800, verified chips, 18.4 km, confidence, and *Why this result?*
   ("the only candidate that satisfied every hard requirement ...").
6. Expand a **Transcript** — PII-redacted turns.

What to point out: claims are linked to calls; UNKNOWN never became VERIFIED
(Anand); early stopping saved two calls; the follow-up was generated by state,
not a script.

## Run 2 — failure path (honesty as a feature)

1. Back to `/verify`, select **Emergency part sourcing (honest failure path)**.
2. Same request — different morning: Metro sold out this morning.
3. Start verification. All six candidates are contacted this time; each fails
   a hard requirement or stays unknown.
4. The banner: **NO FULLY VERIFIED MATCH** with the per-candidate breakdown
   (out of stock / incompatible / over budget / uncertain / unreachable),
   the "Why this result?" explanation, and the operator options (increase
   budget, expand radius, relax deadline, stop).

What to point out: no fake success — the system's most important output when
reality says no is an honest, structured no.

## Determinism

- Personas and their scripts: `lib/demo/scenarios.ts`.
- The goal analyzer is heuristic (no LLM); identical input → identical goals.
- Mock calls advance one stage per poll — realistic pacing, no wall-clock
  dependence.
- The mock adapter never contacts CALL-E; every surface is labeled
  **DEMO MODE (mock CALL-E)**.

## Real CALL-E demo

1. `CALLE_API_KEY=...`, `MOCK_CALL_E=false`, `WEBHOOK_TOKEN=...`,
   `APP_ORIGIN=https://<deployment>` in the environment.
2. Provide real candidates via the manual provider (`POST /api/candidates`
   with `{taskId, candidates:[...]}`) or a scenario's phone numbers.
3. Watch the server logs: `[CALL-E] MODE ...`, `[CALL-E] CALL CREATED ...`,
   `[CALL-E] CALL COMPLETED ...`, `[CALL-E] RESULT RECEIVED ...`,
   `[CALL-E] WEBHOOK RECEIVED ...`.
4. The dashboard works identically — the badge switches to **LIVE CALL-E**.
